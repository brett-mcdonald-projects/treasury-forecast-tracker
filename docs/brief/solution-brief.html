What it does

The report answers one question: how has the economic and fiscal outlook changed across the Treasury's successive forecast rounds? It loads the Treasury's published Economic and Fiscal Update data files for three rounds (Half Year Update 2025, Budget Update 2026 and Pre-election Update 2026) and lets the reader compare any of eight headline measures across them, such as real GDP growth, CPI inflation, the operating balance and net core Crown debt.

I built it to show how I approach a reporting solution on Microsoft Fabric end to end: automated ingestion, a tested data model, and a governed route from source file to published report. It is an independent demonstration on public data and is not a Treasury product.

How it works

What is built and working today

ComponentDetail
Source registryOne row per forecast round with its file address. A new round or a new source is a new row, not a redesign. Four rounds are registered, including Half Year Update 2026, which is not yet published.
Change detectionEach run requests every registered file, hashes it (SHA-256) and compares it with the last loaded hash in the ingest log. Only new or changed files are landed and processed. A missing file is recorded, not treated as a failure.
LakehouseRaw files are kept untouched in a timestamped landing folder. Parsed data is held in eight Delta tables: 12,411 observations across 48 Treasury series and three rounds, 1,421 rows of derived headline measures, plus the registry, ingest log and test results.
Data checksEight tests run before any table is refreshed: row presence, duplicate keys, nulls, referential integrity, required series present in every round, no gaps in the quarterly GDP series, forecast flag complete, and a plausibility range. A failed test stops the refresh.
Semantic modelsA Direct Lake model over the lakehouse, and an import-mode copy for the public report, because Power BI's public publishing does not support Direct Lake.
ReportTwo pages. Forecast tracker: measure selector, chart and table by round. Pipeline and data quality: the ingest log and test results, so the reader can see what the pipeline did.
Result of the run on 8 October 2026: three rounds fetched directly from budget.govt.nz and loaded (HTTP 200); Half Year Update 2026 returned 404 and was logged as not yet published; 8 of 8 data checks passed. When the Treasury publishes that file under its usual naming, the next run will pick it up without a code change.

Design choices

  • Definitions are computed once, in the data layer. Growth rates and percent-of-GDP measures are derived in the notebook, so every report built on the model uses the same calculation.
  • Raw data is never overwritten. Each fetched file is stored as received, so any figure can be traced back to the file it came from.
  • The pipeline reports on itself. The ingest log and test results are tables in the model and are shown in the report.
  • Neutral presentation. The report describes how forecasts moved between rounds. It does not assess forecast quality.
  • One documented heuristic. The economic data file has no forecast flag, so the last quarter with a whole-number CPI index is treated as the last actual. The fiscal file carries its own flag, which is used directly.

How it was built

I set the requirements (one cloud platform, automated ingestion from a predictable public source, change detection, an architecture that can take further sources, and a full release life cycle rather than a one-off build) and chose the subject and approach. I directed an AI assistant (Claude), which wrote the notebook code and carried out much of the Fabric configuration, and I reviewed the results. The decision log and status file in the repository record what was decided and why.

Platform

Microsoft Fabric (lakehouse, PySpark notebook, Direct Lake and import semantic models), Power BI service, GitHub. Built entirely in the browser. Data: the Treasury, Economic and Fiscal Update data files (budget.govt.nz).
